# KUnnect

건국대학교 글로컬 캠퍼스 분실물 웹 서비스(PWA). AI(Claude API)가 사진·위치·태그로 분실글과 습득글을 자동 연결한다. 아래 "KUnnect 기획안"이 제품 계획 문서다.

## 저장소 구성 / 실행 / 배포

| 경로 | 내용 |
|---|---|
| `apps/web/` | 프런트엔드 — Next.js 16 PWA(React 19, TanStack Query). 개발 가이드: `docs/dev-plan-frontend.md` |
| `apps/api/` | 백엔드 — Fastify + Zod + Drizzle + PostgreSQL, 매칭 엔진(`src/matching`). 실행 가이드: `apps/api/README.md`, API 계약: `apps/api/openapi.yaml`(개발 중 `/docs`) |
| `docs/` | 설계·운영 문서 — `dev-plan-backend.md`(백엔드 계획·결정·승인 대기 항목), `dev-plan-frontend.md`, `deploy-backend.md`(배포 가이드, Cloudflare 체크리스트 5.6) |
| `docker-compose.yml` / `docker-compose.prod.yml` | 로컬 개발용 PostgreSQL / 운영용 구성 [미검증] |

**로컬 실행(요약)** — 두 앱 모두 `pnpm` 사용(Node 22+).

```bash
# 백엔드 (apps/api)  — 자세한 순서는 apps/api/README.md
cd apps/api && pnpm install && cp .env.example .env
pnpm db:dev            # (별도 터미널) Docker 없이 PostgreSQL 실행, 또는 docker compose up -d db
pnpm db:migrate && pnpm db:seed && pnpm db:seed:demo   # 시연 시드는 운영 DB 에 실행 금지
pnpm dev               # http://localhost:4000

# 프런트엔드 (apps/web)
cd apps/web && pnpm install && cp .env.example .env.local
# .env.local: NEXT_PUBLIC_API_MOCK=false (실제 API 사용), API_ORIGIN=http://localhost:4000
pnpm dev               # http://localhost:3000  (Next.js rewrites 가 /api/*, /files/* 를 API 로 프록시: 동일 출처, CORS 없음)
```

**배포(요약)** — 프런트는 `apps/web` 에서 `pnpm build && pnpm start`(Next.js 서버), 백엔드는 `apps/api` 를 상시 서버(Node + PostgreSQL + 사진 저장 디스크)로 실행한다. HTTPS 는 앞단(Cloudflare Tunnel 등)에서 종단하고 백엔드 환경 변수 `ALLOWED_ORIGINS`(공개 URL)·`TRUST_PROXY_HOPS`(프록시 대수)를 맞춘다. 상세 체크리스트는 `docs/deploy-backend.md` 5.6.
시크릿(`ANTHROPIC_API_KEY` 등)은 저장소에 커밋하지 않고 서버 환경 변수/`.env`(git 제외)로만 둔다.

# KUnnect 기획안 (데모 범위)

> 표기 규칙: **[확정]** 은 사용자가 결정한 항목, **[가정/제안]** 은 결정되지 않아 임시로 정한 항목이다. 남은 미결정 항목은 [16. 확정 및 미결정 사항](#16-확정-및-미결정-사항) 참조.
> 범위: **데모용 웹 서비스**. 앱 스토어 심사·배포·운영 체계는 범위 밖이다.

## 1. 개요 / 문제 / 목표

**개요**: KUnnect는 건국대학교 글로컬 캠퍼스 대상 분실물 웹 서비스다([확정]). 단순 게시판이 아니라 AI(Claude API)가 사진·정보를 분석해 분실글과 습득글을 자동으로 연결한다.

**문제**
- 기존 분실물 게시판은 분실자가 직접 글을 일일이 뒤져야 한다.
- 같은 물건이 "검은색 에어팟 케이스" / "검은 케이스"처럼 다르게 표현되어 키워드 검색으로 못 찾는다.
- 습득자는 주인을 찾을 방법이 없어 물건이 방치된다.

**목표**
- 분실글과 습득글이 서로 유사하면 시스템이 자동 연결하고 분실자에게 알림을 보낸다.
- 글 작성 부담을 낮춘다(사진은 선택, 위치 + 태그 중심).
- 데모 성공 지표 [가정/제안]: 시연 시나리오(작성 → 매칭 → 알림 → 쪽지 → 인수 완료)가 끊김 없이 동작, 시드 데이터 기준 매칭 정확도 육안 확인.

**예시**: 분실글 "검은색 에어팟 케이스, 학생회관에서 분실" ↔ 습득글 "검은 케이스, 학생회관 2층" → 자동 연결.

## 2. 대상 사용자

| 사용자 | 설명 | 주요 니즈 |
|---|---|---|
| 분실자 | 물건을 잃어버린 캠퍼스 구성원 | 빠르게 되찾기, 알림 받기 |
| 습득자 | 물건을 주운 사람 | 간단히 등록, 주인에게 연결 |

- 관리자/운영 주체: 현재 해당 없음. 운영 기능은 보류한다([확정], 9번).
- 가입은 자체 아이디/비밀번호 방식이며 학교 소속 검증은 하지 않는다([확정], 3번).

## 3. 핵심 기능

1. **분실글 작성**: 사진(선택), 분실 위치/시간, 태그, 설명.
2. **습득글 작성**: 사진(선택), 습득 위치/시간, 현재 보관 장소(습득자 본인 소지 또는 습득자가 적는 장소), 태그, 설명.
3. **사진 첨부**: 선택 사항([확정]). 최대 3장 [가정/제안]. 업로드 시 압축·EXIF 위치정보 제거.
4. **위치 표시**: 캠퍼스 건물/시설 목록 선택 + 지도 핀 [가정/제안]. 목록은 16절 N1 참조.
5. **태그**: 프리셋(스마트폰, 이어폰, 학생증, 지갑, 가방, 열쇠, 노트북 등) + 사용자 정의 태그.
6. **자동 매칭**: 분실글 ↔ 습득글을 사진·위치·태그 3개 신호로 비교, 임계값 이상이면 연결.
7. **알림**: 고유사도 매칭 시 분실글 작성자에게 알림 — "분실하신 물건과 비슷한 물건의 글이 작성되었습니다. 확인해 보세요." 방식은 앱 내 알림 센터(기본) + Web Push(지원 브라우저, 선택) [가정/제안].
8. **매칭 확인/반환 처리**: 분실자가 후보를 확인하고 "내 것이 맞음/아님" 선택 → 쪽지 대화에서 소유 확인·인수 협의 → 완료 처리.
9. **댓글**: 글에 공개 댓글 작성·수정·삭제, 대댓글 1단계, 작성자 알림, 신고. [14절](#14-댓글-기능-상세).
10. **쪽지(1:1 DM)**: 글 또는 사용자 프로필에서 시작하는 1:1 비공개 대화, 쪽지함, 읽지 않음, 알림, 차단/신고. 인수 협의의 유일한 경로(분실물센터 연동 없음). [15절](#15-쪽지11-dm-기능-상세).

## 4. 사용자 흐름

```
[분실자]  가입/로그인 → 글 작성 → (대기) → 알림 수신 → 매칭 후보 확인 → "내 것" 선택
          → 습득자와 쪽지 → 소유 확인 → 인수 → 반환 완료
[습득자]  글 작성 → 시스템이 분실글과 비교 → 매칭 시 분실자에게 알림
          → 쪽지 수신 → 소유 확인 후 전달 → 완료
[누구나]  글 상세에서 댓글 작성 / 개인 문의는 "쪽지 보내기"(글 또는 프로필에서)
[시스템]  글 등록(트리거) → 반대 유형 글 후보 추출 → 점수 계산 → 임계값 이상 → 연결 + 알림
```

- 새 습득글은 기존 분실글들과, 새 분실글은 기존 습득글들과 모두 비교한다(양방향).
- 알림 대상은 분실글 작성자(사양). 습득자에게는 쪽지가 오거나 자기 글에 댓글이 달릴 때 알린다 [가정/제안].

## 5. 매칭 알고리즘 설계

### 5.1 파이프라인

1. **후보 필터(저비용)**: 반대 유형, 활성 상태, 시간 조건(습득 시각 ≥ 분실 시각 − 여유), 카테고리 태그 충돌 제외.
2. **신호별 점수**: 위치·태그는 로컬 계산, 사진은 Claude 비전 사용(사진이 있는 경우만).
3. **가중 합산 → 임계값 판정 → 연결/알림.**

### 5.2 신호별 점수 (각 0~1)

| 신호 | 계산 방법 [가정/제안] |
|---|---|
| **사진 유사도** | 게시 시 Claude 비전으로 사진을 구조화 JSON(카테고리, 색상, 브랜드, 형태, 특징)으로 1회 저장. 매칭 시 속성 일치도를 계산하고, 상위 후보만 Claude로 두 사진을 직접 비교해 0~1 점수와 근거를 받는다. |
| **위치 유사도** | 같은 건물=1.0, 같은 건물 다른 층/인접 건물=0.6~0.8, 거리에 따라 감쇠. 건물 ID/좌표 기반. |
| **태그 유사도** | 프리셋은 정확 일치(Jaccard). 사용자 정의 태그는 정규화 후 동의어/임베딩 유사도로 보정. 카테고리 태그 불일치 시 강한 감점. |

### 5.3 가중치와 임계값 [확정]

```
score = 0.45*photo + 0.25*location + 0.30*tag   # [사용자 결정] 이전 0.5/0.25/0.25, 사진 점수에 색상 규칙(색 유사 시 하한) 적용, 색 하한만으로는 AI 점수 0.5 미만이면 AUTO 불가(사용자 승인)
score ≥ 0.80          → 자동 연결 + 알림
0.60 ≤ score < 0.80   → 연결 후보로만 표시(앱 내 "비슷한 글" 목록, 알림 없음)
score < 0.60          → 무시
```

### 5.4 사진이 없는 경우 [가정/제안]

사진은 선택이므로 어느 한쪽이라도 사진이 없으면 사진 신호를 제외하고 가중치를 재정규화한다.

```
사진 없음(한쪽 이상):  score = 0.5*location + 0.5*tag
```

- 신호가 2개뿐이라 오탐 위험이 크다. 이 경우 자동 알림 임계값을 **0.85로 상향**하고(0.60~0.85는 후보 표시만) 위치·태그 외에 설명 텍스트를 Claude로 보조 비교할 수 있다 — 상향 수치는 제안이며 확정 필요.
- 한쪽만 사진이 있으면 사진은 비교하지 않고 사진 속성 JSON의 카테고리·색상만 태그 점수 보정에 참고한다.

### 5.5 Claude API 사용 방식

- **게시 시(1회/글)**: 사진 → 속성 JSON 추출(비전), DB에 저장해 재사용.
- **매칭 시(후보 상위 N개만)**: 두 글의 사진·태그·설명을 구조화 출력으로 비교해 0~1과 근거를 받는다.
- **비용/지연**: 사전 필터와 위치·태그 점수로 먼저 거르고, 사전 점수가 낮으면 호출하지 않음. 속성 JSON 캐시, 후보 상위 N(예: 5) 제한, 이미지 리사이즈(긴 변 ~1024px). 매칭은 글 등록 후 백그라운드로 비동기 처리(화면은 즉시 응답). 모델 선택·예산은 보류(16절 #11), 데모 기본값은 소형 모델 [가정/제안].
- **한계**: 흔한 물건은 구분이 어렵다 → 최종 확인은 항상 사람(분실자)과 쪽지 내 소유 확인이 한다.

- 신고는 저장만 하며 처리 절차는 보류한다(9번 해당 없음).

## 7. 시스템 아키텍처 (데모)

```
[웹 클라이언트(PWA)] ──HTTPS──> [웹 서버/API] ──> [DB]
                                    │  ├────────> [사진 저장소]
                                    │  └─ 비동기 작업 ─> [매칭 작업]
                                    │                      ├─> Claude API
                                    │                      ├─> DB (후보 조회, Match/Notification 저장)
                                    │                      └─> Web Push (선택)
                                    └─ 폴링 <── 클라이언트(알림·쪽지)
```

- 글 등록 API는 저장 후 매칭을 백그라운드로 실행하고 즉시 응답한다. 별도 큐(Redis)는 두지 않는다 [가정/제안].
- 알림은 DB `Notification` 기반의 앱 내 알림 센터가 기본이고, Web Push는 구독한 사용자에게만 추가 발송한다 [가정/제안].
- 쪽지·알림 갱신은 폴링([확정], 18번). WebSocket은 이후 단계.
- 댓글 작성 시 서버에서 연락처 패턴(전화번호·이메일·SNS ID)을 탐지해 마스킹한다([확정], 17번). 쪽지에는 제한이 없다.
- Claude API 키는 서버에만 보관한다.
- 만료 정리: 종료 후 쪽지 30일 / 글 90일 경과 데이터는 주기 작업으로 삭제([확정], 10·16번).

## 8. 기술 스택 (데모)

| 영역 | 제안 [가정/제안] | 비고 |
|---|---|---|
| 플랫폼 | **반응형 웹 + PWA** [확정] | 스토어 심사·빌드 없음. 모바일 브라우저 우선 레이아웃 |
| 프런트엔드 | React / Next.js (PWA) | 기존 제안의 React Native는 웹에 부적합하여 변경 |
| 백엔드 | Next.js API Routes 또는 Node.js(TypeScript) | 데모는 단일 서버로 단순화 |
| DB | PostgreSQL(로컬 시연은 SQLite 가능) | 호스팅 환경 미정 |
| 사진 저장 | 서버 로컬 디스크 또는 호스팅 제공 스토리지 | S3 도입은 이후 |
| 비동기 | 서버 내 백그라운드 처리 | Redis 큐 제외 |
| AI | Claude API (비전, 구조화 출력) | 사양 고정 |
| 알림 | 앱 내 알림 센터 + Web Push(선택) | FCM/APNs 제외. iOS Web Push는 홈 화면 설치(PWA) 필요 |
| 인증 | 자체 아이디/비밀번호([확정]), 비밀번호 해시(bcrypt/argon2), 세션 쿠키 | 학교 이메일·SSO 없음 |
| 지도 | 시설 목록 + 지도 SDK | 지도 제공자 미정 |

## 9. 화면 목록 (텍스트 와이어프레임)

1. **회원가입/로그인**: `[아이디] [비밀번호] [닉네임] [가입 / 로그인]`
2. **홈(피드)**: `[분실 | 습득 탭] [검색/필터] / 글 카드 리스트(사진 있으면 썸네일·제목·위치·시간) / [+ 글쓰기]`
3. **글 작성(분실/습득)**: `[유형] [사진 추가 0~3(선택)] [제목] [위치 선택(목록/지도)] [일시] [태그: 프리셋 칩 + 직접 입력] [설명] [(습득) 보관 장소] [등록]`
4. **글 상세**: `[사진 캐러셀(있을 때)] [제목/상태] [위치] [태그] [설명] [쪽지 보내기] [신고]` + 하단 **댓글 목록**(`[댓글 입력] [등록]`, 각 댓글: 닉네임·시간·`[답글][수정][삭제][신고]`)
5. **매칭 결과**: `내 글 요약 / 후보 카드(유사도 등급·위치 차이·AI 근거 한 줄) / [내 것이 맞아요] [아니에요]`
6. **알림 센터**: `알림 항목(문구·시간·읽음) → 탭 시 유형별 이동(매칭 결과 / 해당 댓글 / 쪽지 대화)`
7. **쪽지함**: `[대화 목록: 상대 닉네임·마지막 메시지·시간·읽지 않음 배지]`
8. **쪽지 대화**: `[상단: 상대 닉네임·(글 맥락 링크)·⋯(차단/신고/나가기)] [말풍선] [입력창 + 전송] [(인수 협의) 소유 확인 질문 / 인수 완료 요청]`
9. **사용자 프로필**: `[닉네임] [작성한 공개 글 목록] [쪽지 보내기] [차단/신고]`
10. **내 활동**: `내가 쓴 글 / 내 댓글 / 상태 변경(반환 완료·삭제)`
11. **설정**: `알림 on/off(매칭·댓글·쪽지 개별), Web Push 구독, 차단 목록, 비밀번호 변경, 로그아웃`

## 10. 개인정보 / 안전 고려사항

- **익명성 [가정/제안]**: 화면에는 닉네임만 노출한다. 계정은 아이디/비밀번호만으로 생성되어 실명·학번·이메일을 수집하지 않으며, 서버 내부에서는 `user_id`로 식별한다. 따라서 차단은 `user_id` 기준으로 동작하고(상대 닉네임을 바꿔도 유지), 신고는 대상의 `user_id`와 신고 시점 내용(`snapshot`)을 저장한다. 닉네임 중복·변경 규칙은 미정(16절).
- **사진**: 업로드 시 EXIF(GPS 포함) 제거. 얼굴·학생증 번호 등 민감 정보 노출 주의 안내. 학생증/카드 사진은 공개 시 블러 또는 비공개 [가정/제안]. Claude API로 사진이 전송됨을 이용 안내에 명시. **[사용자 결정] 학생증·카드·지갑 등 민감 사진은 AI(Claude)로 전송하지 않고(`AI_SENSITIVE_MODE` 기본 SKIP, 흐림 사본도 미전송) 태그·위치만으로 매칭한다.**
- **위치**: 건물/층 단위로만 공개, 실시간 위치는 수집하지 않는다.
- **본인 확인(소유 검증)**: 습득글은 물건 일부 특징을 비공개로 두고, 쪽지에서 소유자 후보가 이를 맞히도록 한다. 습득자가 공개 글에 모든 특징을 적지 않도록 안내.
- **인수 안전**: 인수는 앱 내 쪽지로만 협의한다. 앱은 연락처 입력란을 제공·공개하지 않는다([확정], 7번). 인수 장소는 사람이 많은 공공장소 권장 [가정/제안].
- **댓글 개인정보**: 전화번호·이메일·SNS ID 패턴은 등록 시 마스킹, "개인 연락은 쪽지로" 안내를 표시한다([확정], 17번).
- **쪽지**: 연락처 패턴 제한·경고 없음([확정], 17번). 신고 시 최근 N건을 `snapshot`으로 저장하며 별도 열람 주체는 없다(운영 기능 보류). 차단 시 새 쪽지·알림 차단. 종료 후 30일 뒤 삭제([확정], 16번).
- **남용 방지**: 신고·차단, 작성/대화 생성 빈도 제한. 신고 처리·자동 숨김 기준은 보류.
- **데이터 보존**: 종료된 글은 90일 후 삭제 또는 익명화([확정], 10번).
- **알림 문구**: 알림/푸시에 물건 상세·위치를 담지 않는다. 사양 문구 그대로 사용.
- **계정 복구 [가정/제안]**: 이메일을 수집하지 않으므로 데모에서는 비밀번호 찾기를 제공하지 않는다.

## 14. 댓글 기능 상세

**정책**
- 작성 권한: 로그인한 사용자 누구나(글 작성자 포함). [가정/제안]
- 구조: 대댓글 1단계. [가정/제안]
- 수정/삭제: 작성자 본인만. 수정 시 "수정됨" 표시, 답글이 있는 삭제는 "삭제된 댓글입니다"로 자리 유지. [가정/제안]
- 글 상태가 RETURNED·CLOSED면 새 댓글 비활성. [가정/제안]
- 연락처 패턴(전화번호·이메일·SNS ID)은 등록 시 마스킹, "개인 연락은 쪽지로" 안내 표시. [확정, 17번]
- 길이·빈도 제한, 신고 후 숨김 기준 등 세부 **댓글 정책은 사용자 제공 예정 → 미결정(16절 #14)**. 아래 수치는 임시값이다: 300자, 분당 5건. [가정/제안]
- 알림: 글 작성자에게 새 댓글, 답글은 원 댓글 작성자에게. 본인 댓글은 제외. [가정/제안]
- 신고: 댓글별 신고(사유 선택), 저장만 하며 처리·자동 숨김은 보류.

**흐름**: 글 상세 → 댓글 입력 → 등록 → 글 작성자 알림 → 탭 시 해당 댓글로 이동 → 답글/쪽지 전환.

**화면**: 글 상세 하단 댓글 영역(9절 4번), 알림 센터 이동.

**데이터/API**: `Comment`, `Report`, `Notification`(6절). `POST/GET /posts/{id}/comments`, `PATCH/DELETE /comments/{id}`, `POST /reports`.

**MVP 범위**: 위 정책 전체 포함 [확정, 13번]. 이후: 멘션, 신고 처리.

**리스크**: 연락처 노출, 괴롭힘, 습득 물건 특징 공개로 허위 인수 유도.

## 15. 쪽지(1:1 DM) 기능 상세

**기존 가정과의 정리**: "앱 내 메시지 + 소유 확인 질문"은 별개 기능이 아니라 **쪽지의 한 사용처**다. `HandoverRequest`는 `Conversation`과 연결된 상태 객체이고, 소유 확인 질문/답변은 쪽지 내 구조화 메시지(`VERIFY_QUESTION`/`VERIFY_ANSWER`)다. 별도 "인수 절차" 화면은 없다. 분실물센터 연동·연락처 공개는 범위에서 제외한다([확정], 7번).

**정책**
- 시작: **글 상세 또는 사용자 프로필**에서 시작([확정], 15번). 자기 자신에게는 불가.
- 대화 단위: 사용자 쌍당 대화 1개 재사용, 글에서 시작하면 첫 메시지에 글 맥락 첨부. [가정/제안]
- 메시지: 텍스트 전용, 최대 1,000자. [가정/제안]
- 읽지 않음: `last_read_message_id` 기준 쪽지함 배지.
- 알림: 새 쪽지 알림(본문 미리보기 없음), 대화별 음소거. [가정/제안]
- 차단: 새 쪽지·알림 차단, 기존 대화 읽기 전용, 상대에게 차단 사실 비노출. [가정/제안]
- 신고: 메시지/사용자 신고 시 최근 N건을 `snapshot`으로 저장. 처리 절차는 보류.
- 연락처 패턴: 쪽지에는 마스킹·경고 없음([확정], 17번).
- 보존: 대화 종료(반환 완료/글 종료) 후 30일 삭제([확정], 16번).
- 남용 방지: 신규 대화 생성 일일 상한. [가정/제안]
- 익명: 닉네임만 노출(10절).

**흐름**
```
글 상세/프로필 → [쪽지 보내기] → 대화 생성 → 상대 알림 → 쪽지함 → 대화
→ (습득자) 소유 확인 질문 → (분실자) 답변 → 습득자 판단
→ 인수 장소·시간 합의 → [인수 완료] 양측 확인 → Post 상태 RETURNED
```

**화면**: 쪽지함, 쪽지 대화, 사용자 프로필(9절 7·8·9번), 설정의 차단 목록.

**데이터/API**: `Conversation`, `ConversationMember`, `Message`, `Block`, `HandoverRequest.conversation_id`(6절). `POST /conversations`, `GET /conversations`, `GET/POST /conversations/{id}/messages`, `POST /conversations/{id}/read`, `POST/DELETE /blocks`, `POST /reports`. 실시간은 폴링(앱 열려 있을 때 5~10초) [확정, 18번].

**MVP 범위**: 위 정책 전체 포함 [확정, 13번]. 이후: 소유 확인 UI 고도화, WebSocket, 이미지 첨부.

**리스크**: 괴롭힘/스팸, 앱 밖 연락처 교환 유도, 신고 처리 주체 부재, 메시지 보존·폴링 부하.
